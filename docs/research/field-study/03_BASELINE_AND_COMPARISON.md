# Existing-tools baseline and conditional low-fidelity comparison

**Status:** Public vendor claims checked 25 October 2026; no app installed, device feature independently reproduced, user workflow observed or comparison administered. **Do not run Stage B before the discovery decision and approved consent/copy.**

## 1. Current claims are not task performance evidence

| Source | What its own material says | Verification and research use |
|---|---|---|
| [MAWAQIT API policy](https://help.mawaqit.net/en/articles/11991838-can-i-use-your-api) | The published API is private; official direct prayer-time URL/widget may be supplied on request | Vendor statement, **not** API permission, app integration or availability proof |
| [Masjidbox help](https://support.masjidbox.com/does-masjidbox-have-a-public-api-for-prayer-times-sfnfd) | No public prayer API; iCal subscription and CSV/Excel export routes advertised | Vendor statement, **not** tested update frequency, access entitlement or lawful data reuse |
| [Pillars prayer-time page](https://thepillarsapp.com/prayer-times-app) | Advertises offline phone-based prayer calculations and free prayer-time tools | Vendor statement, **not** verified behavior on particular phones/versions |
| [Pillars FAQ](https://thepillarsapp.com/faqs) | Discusses notifications, methods and background-related limitations | Dated/version-sensitive FAQ; do not assume every statement describes today's app |
| Apple/Google Calendar or paper planner | A participant may already have a workable system | Directly observe their actual setup or reproduce with **synthetic** data; no automatic assumption their baseline is inferior |

**Firsthand baseline inspection record (complete privately, only aggregated publicly):** participant-approved tool names; OS/app version if voluntarily shared; region and calendar type; actual task and steps; successful/no-conflict cases; failure/uncertainty; manual import vs live subscription; setup and repeated correction cost; notification choices; user-provided source trust; unknown/restricted features. No screenshots or identifiable account details without separate approved permission.

Before claiming a vendor has an unmet-feature gap, test the same relevant task yourself on a legally accessible current build or label it **not independently checked**. Never scrape undocumented APIs.

## 2. Separate problem discovery from comparison

Stage A interviews do **not** show the proposed planner. Only if the dated discovery decision supports an actionable underserved problem should a designer make *one* paper/clickable reversible planning interaction from the 19 candidate **contracts**, not 19 screens.

Any prayer-time or fiqh-dependent copy requires **qualified human review of the exact text and behavior** before participants see it. Until then use **neutral synthetic time constraints**. Do not introduce “leave now for Iqamah”, obligatory prayer interpretation or religious permission in a test task.

## 3. Fixed, synthetic test cards — not real religious timings

Use comparable difficulty and verified expected outcomes in **both** conditions. A researcher must pilot for ambiguity *without counting the pilot as evidence*, then freeze cards and scoring before the first comparison.

**Card A — Solvable overlap**

> A fixed appointment is scheduled **14:00–15:00**. A flexible 20-minute personal activity was provisionally put at **14:30–14:50**; it is allowed any time **13:00–16:30**. Find an achievable next step without moving the fixed appointment. The person may keep the original plan if they prefer, but should recognize the conflict.

Expected factual boundary: activity overlaps the fixed event; alternatives include 13:20–13:40 or 15:10–15:30, if no other facts constrain them. Never mark a preference for no automatic change as moral or religious failure.

**Card B — No-conflict / no-action control**

> A fixed appointment is **14:00–15:00**. The flexible activity is **15:15–15:35**, allowed **13:00–16:30**. Decide whether a scheduling intervention is necessary.

Expected boundary: no overlap requiring intervention. Inventing a conflict or sending an unnecessary reminder is an error. “Keep as is” is a valid successful outcome.

**Card C — Structural/no-authority case**

> The person's required duty is **13:00–17:00** with no permission to leave or change the hours. Another person's presence is needed **14:00–15:00**, and only that other person or a supervisor can authorize a change. No authorization has been granted. Decide what, if anything, the planner may change.

Expected boundary: **no authorized unilateral reschedule**. Displaying uncertainty, preserving commitments, or suggesting a respectful human coordination request is acceptable; silently changing either duty or implying permission is a **critical error**.

Cards are neutral, fabricated and need no prayer calculation. One-off experiment results on synthetic tasks cannot establish demand in everyday life.

## 4. Compare fairly

**A:** Participant's current planner/calendar/paper + trusted information source, configured fairly, with a brief opportunity to learn an unfamiliar feature. **B:** Minimal paper/clickable reversible decision concept with **the same supplied data and timing facts**. Do not give the prototype extra knowledge or omit natural baseline workarounds. Use fresh synthetic entries so no real schedule is exposed.

- Alternate condition order A→B and B→A when sample/access permits; rotate Card A/C and retain Card B for negative control. Record if counterbalancing is impossible.
- Do not equate a paper sketch's theoretical click with actual device speed or reliability. Separately measure future setup, duplicate entry and correction cost.
- Start each condition with the same task statement; allow participants to choose **no tool / paper** as a baseline.
- Record whether a participant can explain the facts, constraints, chosen option and ability to undo. Check when they incorrectly think a planning suggestion is religious permission.
- Quiet-default test: no alerts without opt-in; denial must preserve on-demand use. A paper test proves **comprehension**, not OS notification delivery.
- Always debrief, invite corrections and record any preference for existing tools or no app.

## 5. Predefine measures and critical failures

| Measure | Minimum observable record |
|---|---|
| Task correctness | Correctly identifies an overlap or no conflict; does not fabricate a feasible action |
| Agency / reversibility | Explicit user choice, can explain undo; no silent edit |
| Burden | Time, number of information switches, setup entries and probable recurring edits **separately** |
| Comprehension | Teach-back of source, unknowns, difference between suggestion vs authorization |
| Negative cases | Keeps no-conflict case unchanged; never claims permission in Card C |
| Harm and privacy | Participant discomfort, misleading confidence, disclosure request, pressured reminders |
| Accessibility | Screen-reader, large-text or reading-order failures (only when relevant accessibility materials are actually tested) |
| Preference after debrief | Chosen baseline/worksheet/prototype **and reason**, not “do you like our app?” |

**Safety stop:** a consequentially misleading religious claim, coerced disclosure, confident unauthorized action or harmful scheduling instruction stops exposure until redesigned/reviewed. For any unreviewed material, only use the neutral cards.

## 6. Decision criteria — freeze before sessions

The owner and independent research reviewer must specify what constitutes a **material, replicated within-sample advantage**, an acceptable setup/maintenance burden, and how many or what severity of errors forces a stop. Record the chosen rule, justification, date, study version, and any post-hoc amendments **privately** before recruitment/comparison.

Do not adopt “2 of 10 interviews” or “most people preferred it” as a universal proof. Small samples support a bounded **investment choice**, not a prevalence estimate or claim of efficacy. A one-task result only authorizes considering the next small test, not a production release.
